About the Benchmark

PAARBench (PlanActAdaptRepeatBench) evaluates test-time adaptation (TTA) strategies for latent world models in closed-loop control. Each submission declares at most two tunable hyperparameters; the harness runs a fixed selection protocol (3-point grid per axis on the selection cohort, up to two boundary expansions), freezes the best configuration, and evaluates once on held-out test cohorts.

What it tests

Whether a world model can adapt online during MPC replanning — and whether that adaptation helps control without compounding error, catastrophic failures, or hidden tuning cost.

Environments

PushObj — pushing objects of varied shapes.
PushT — visual pushing with distribution shift.

Fixed planner

Goal horizon 25, 100 gradient-descent steps, zero action initialization, no action noise. Deterministic closed-loop for paired episode comparisons.

Metric frontier

Success rate (with binomial SE in parentheses) plus paired distance change, catastrophe rate, regret, adaptation latency, and peak memory — not a single rank.

How It Works

The evaluation protocol has four stages:

  1. Selection — On settings with a selection cohort, the standard protocol evaluates a 3-point grid per tunable axis (up to two boundary expansions). Every cell is counted as selection cost.
  2. Freeze — The best hyperparameters (per the rule's objective) are frozen.
  3. Test — The frozen configuration runs once on each held-out test cohort. For pushobj_shift, parameters are inherited from PushObj with no new selection.
  4. Record — Compact results go to results/<method>/<setting>.json. All continuous metrics are paired against the frozen baseline on the same episodes.

Methods that own mutable shared state (model weights plus an optimizer) must declare requires_episode_isolation: true so each episode is evaluated independently.

Settings

Each setting pairs a base world model with a fixed episode distribution. Hyperparameter tuning uses one selection cohort (seed 0); leaderboard scores are pooled over three held-out test cohorts (seeds 100, 200, and 300). Selection and test draws are always disjoint.

PushObj (pushobj) is the primary object-pushing setting: checkpoint pushobj_shape_shift, shapes T, L, Z, and +. Methods select hyperparameters on seed 0, then run once on each test seed.

PushObj Shift (pushobj_shift) holds out different shapes (I, small_tee, square) on the same checkpoint. There is no selection cohort — parameters are frozen from PushObj — but evaluation still uses the same three test seeds.

PushT (pusht) is the visual pushing setting on pusht_visual_shift with shapes T, L, and Z. It follows the same one-seed selection, three-seed evaluation layout as PushObj.

Success rate is the weakest column here. At these sample sizes its binomial standard error is around 0.02, so adjacent rows are usually not separable on it. The continuous columns carry far more information:

  • median dist Δ — median paired change in final distance-to-goal vs. the frozen model on the same episodes (both-fail episodes only). Negative is better.
  • catastrophe — fraction of episodes ending more than 2× further from the goal than frozen. How often adapting actively hurts.
  • regret — fraction of episodes where adapting ended further from the goal than not adapting, and the 90th-percentile size of that loss.
  • adapt s/replan and peak MB — adaptation cost around the adapter hooks only.

Intervals are 95% percentile bootstrap over episodes (2000 resamples). There is deliberately no overall rank — sort by whichever column matters for your use case.

How to Contribute

A submission is an adaptation method with its hyperparameters chosen by the fixed selection protocol, evaluated under that protocol, with its result record included.

Prerequisites

ArtifactHow to get itNeeded for
Base + adapter checkpoints (~1.1 GB) scripts/download_checkpoints.py all Everything
Goal files data/pushobj_eval/val_<shape>/plan_targets.pkl scripts/download_targets.py Everything
Training trajectories (~1 GB) scripts/download_data.py Methods using offline data only
  1. Create your method Copy methods/_template/ to methods/my_method/ and implement adapter.py, method.yaml, and optionally a tunable: block. No benchmark registry or planner changes are required.
  2. Validate locally 
    .venv/bin/python scripts/validate_method.py my_method
.venv/bin/python -m pytest -q
  3. Run the full protocol 
    .venv/bin/python scripts/evaluate.py my_method --setting pushobj --gpus 0,1,2,3
    Also run the frozen baseline for paired metrics: 
    .venv/bin/python scripts/evaluate.py --frozen --setting pushobj
  4. Open a pull request Include your methods/<name>/ directory (with README), the results/<name>/<setting>.json records, and your row(s) added to LEADERBOARD.md. Do not regenerate the full leaderboard — add only your rows.

Full adapter interface documentation is in methods/README.md and CONTRIBUTING.md in the repository.
